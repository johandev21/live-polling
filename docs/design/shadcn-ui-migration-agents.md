# Parallel Shadcn UI Migration

## Mission

Refactor the frontend from the previous custom design-library wrappers to the installed shadcn/ui components.

The migration must:

- Preserve the existing application layout, route structure, responsive behavior, copy, domain behavior, loading states, error states, and accessibility semantics.
- Use the installed shadcn components as the default UI primitives.
- Keep shadcn's default component styling and semantic design tokens. Do not recreate the old design library's visual treatment in new wrappers.
- Make the work safe for multiple agents operating in parallel.
- Leave the frontend build, tests, and lint passing.

This is a component-library migration, not a product redesign.

## Important Vocabulary

Use the project vocabulary consistently:

- **Host**: authenticated person who owns and controls sessions.
- **Participant**: anonymous person who joins a session and submits responses.
- **Session**: host-owned live event containing polls and participant activity.
- **Poll**: question within a session.
- **Response**: participant's submitted answer.

Do not rename domain concepts while replacing UI components.

## Current Foundation

The frontend is the Vite app at `apps/frontend`.

The shadcn setup is already installed and configured:

- Components: `apps/frontend/src/components/ui`
- Utilities: `apps/frontend/src/lib/utils.ts`
- Hooks generated by shadcn: `apps/frontend/src/hooks`
- shadcn configuration: `apps/frontend/components.json`
- Tailwind entrypoint and shadcn tokens: `apps/frontend/src/index.css`
- Global tooltip provider: `apps/frontend/src/app/entrypoint.tsx`

Use these import paths:

```tsx
import { Button } from '@/components/ui/button';
import { Card, CardContent, CardHeader, CardTitle } from '@/components/ui/card';
import { Input } from '@/components/ui/input';
import { Label } from '@/components/ui/label';
import { cn } from '@/lib/utils';
```

Do not create a literal `@` directory. `@` is an import alias for `src`, not a filesystem directory.

Do not place new shadcn components in `src/shared/ui`. New shadcn primitives belong in `src/components/ui`.

## Multi-Agent Operating Rules

Multiple agents will work on this migration at the same time. Every agent must follow these rules:

1. Work only inside the ownership boundary assigned below.
2. Do not edit another agent's page directory, test files, shared UI files, CSS, package files, routing, or configuration unless the coordinator explicitly assigns that work.
3. Do not run `pnpm dlx shadcn add`, `shadcn init`, or regenerate components. The shadcn component set is already installed.
4. Do not modify `components.json`, `package.json`, `pnpm-lock.yaml`, `vite.config.ts`, `tsconfig*.json`, or `src/index.css` during page migration.
5. Do not modify files under `src/components/ui` during page migration. Treat them as an installed dependency surface.
6. Do not edit or delete files under `src/shared/ui` during page migration. Shared-library cleanup happens in a separate phase.
7. Do not change route definitions, query hooks, mutation hooks, API clients, models, contracts, or server code.
8. Do not change component public props or callback behavior unless required to preserve an existing shadcn API usage.
9. Avoid broad formatting or lint-fix commands that touch files outside the ownership boundary.
10. If an existing shared primitive blocks the migration, use shadcn directly in the owned page rather than changing the shared primitive.
11. If a change appears necessary outside the boundary, record it in the handoff instead of making the change.
12. Re-read the current file before editing. Other agents may have changed unrelated files since the task was assigned.

Agents may commit independently only if the coordinator requests commits. Otherwise, leave changes in the shared worktree and report the exact files changed.

## What Counts as a Successful Page Migration

For each owned page:

- Replace imports from `@/shared/ui` or its subpaths when the imported item is a UI primitive that shadcn provides.
- Prefer direct imports from `@/components/ui/*`.
- Use shadcn primitives such as `Button`, `Card`, `Badge`, `Alert`, `Input`, `Textarea`, `Label`, `Checkbox`, `RadioGroup`, `Tabs`, `Dialog`, `AlertDialog`, `Tooltip`, `Separator`, `Progress`, `Skeleton`, and `Table` where they match the current behavior.
- Use `cn` for conditional class composition instead of ad-hoc class-string concatenation.
- Preserve the page's current layout hierarchy and responsive breakpoints unless a shadcn component requires a small structural wrapper.
- Preserve form labels, descriptions, validation messages, disabled states, keyboard behavior, focus behavior, and ARIA attributes.
- Preserve loading, empty, error, success, live, ended, and waiting states.
- Preserve event handlers and callback payloads exactly.
- Keep page-specific composition in the page slice. Do not add page-specific code to `src/components/ui`.
- Add or update tests only within the owned page directory when behavior or accessible roles need coverage.

## Styling Rules

Use shadcn's default styling as the baseline:

- Prefer component variants (`variant`, `size`) over custom restyling.
- Prefer semantic classes such as `bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, `bg-primary`, and `text-primary-foreground`.
- Do not copy the old `var(--color-*)` styling into new component implementations unless it is required to preserve an existing product-specific layout token and the coordinator approves it.
- Do not add a new global color palette, radius system, shadow system, or typography system.
- Do not use arbitrary one-off color values to recreate the old library.
- Keep existing layout classes, max widths, grids, spacing, and responsive breakpoints when they define the product layout.
- Use `TooltipProvider` already installed at the app root. Do not add nested providers to individual pages unless there is a concrete interaction requirement.
- Use `Tooltip`, `TooltipTrigger`, and `TooltipContent` from `@/components/ui/tooltip` for tooltips. Do not build custom hover-tooltip markup.

## Coordination Protocol

The coordinator should dispatch Agents A-D in parallel first. Each agent must report:

- Files changed.
- Components migrated.
- Legacy shared UI imports remaining in its owned files.
- Tests added or updated.
- Any required change outside its ownership boundary.
- Validation commands and results.

After A-D report completion, dispatch Agent E. After E reports completion, dispatch Agent F.

If the repository uses separate branches or worktrees, merge in this order:

1. Agent A-D branches in any order.
2. Resolve only true overlapping edits. Do not accept broad formatter rewrites.
3. Agent E shared UI cleanup.
4. Agent F integration and final verification.

If all agents share one worktree, agents must not run broad auto-fix commands and must avoid touching files outside their ownership list.

## Search Commands

Run these from the repository root or adjust paths for the agent's worktree:

```powershell
rg "@/shared/ui|shared/ui" apps/frontend/src/pages apps/frontend/src/app apps/frontend/src/shared
rg "from ['\"]@/components/ui/" apps/frontend/src
rg "from ['\"]@/shared/ui" apps/frontend/src
rg "<TooltipProvider|TooltipProvider" apps/frontend/src
rg "var\(--color-|@base-ui|shared/ui" apps/frontend/src/pages
```

The final migration should have no page imports from legacy `@/shared/ui` when a matching shadcn primitive exists.

## Validation

Every page agent should run targeted tests for its owned page area when practical. The integration agent must run:

```powershell
pnpm --filter frontend build
pnpm --filter frontend test
pnpm --filter frontend lint
pnpm --filter frontend format:check
```

Known acceptable outcomes must still be reported:

- Existing React `act(...)` warnings in tests are warnings, not proof of a successful migration.
- shadcn-generated Fast Refresh warnings may appear because component files export variants or helpers.
- Existing Vite bundle-size warnings are not migration failures.

Any TypeScript error, failed test, broken import, missing provider, accessibility regression, or changed callback behavior is a migration failure and must be fixed before completion.
